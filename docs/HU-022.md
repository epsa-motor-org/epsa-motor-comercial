# HU-022 / EMT-145 — Corregir la relación entre comprador y moto

## Alcance y permisos

La API permite corregir una venta existente sin cancelarla ni crear otra venta. Solo **Gerente** y **Administradora** pueden consultar el preview, corregir y consultar el historial. Express aplica el permiso y cada RPC vuelve a verificar el usuario activo y su rol desde `auth.uid()`; la identidad no se toma del request. El Vendedor recibe `403` aunque haya creado la venta o sea su responsable comercial.

Motor y chasis identifican la unidad; modelo y color se muestran como contexto. No se editan ubicación, movimientos, preparación, proveedor, techo físico, pagos, adelanto, snapshots financieros ni comprobante externo.

## Preview individual

`GET /api/ventas/:codven/correccion-relacion`

Respuesta `200` con `{ ok: true, data: { venta, advertencias } }`. `venta` incluye `codven`, `versionRelacion`, comprador, unidad (motor, chasis, modelo, color, estado comercial y dato visible de techo físico), desglose financiero, pagos, adelanto confirmado, comprobante externo, decisión comercial de techo y separación vinculada. No se incluye evidencia privada ni payload interno de idempotencia.

El preview es informativo. La confirmación vuelve a consultar y bloquear las filas. `versionRelacion` debe enviarse como `versionEsperada`.

## Corrección individual

`POST /api/ventas/:codven/correccion-relacion`

Headers requeridos: `Authorization: Bearer <token>` y `Idempotency-Key: <UUID>`.

```json
{
  "motivo": "Se asignó la unidad incorrecta durante el trámite",
  "versionEsperada": 3,
  "codcliNuevo": 25,
  "coduniNuevo": 41
}
```

`motivo` y `versionEsperada` son obligatorios. Se debe enviar al menos uno entre `codcliNuevo` y `coduniNuevo`. Los IDs omitidos mantienen el valor actual; `codusu`, actor, rol, responsable y cualquier campo adicional se rechazan con `400`. Solo se aceptan compradores activos. La unidad destino debe estar identificada y libre de ventas vigentes y separaciones activas. El techo físico/comercial y el snapshot de precio se validan; no se recalcula el precio pactado.

La confirmación vuelve a validar la relación/version y bloquea en una transacción la venta y ambas unidades. Si A deja de ser la unidad de la venta, solo queda `Disponible` cuando no conserva otro compromiso vigente. Otra venta vigente conserva `Vendida`; una separación `Activa` conserva `Separada`; un movimiento HU-003 en `Pendiente` o `En transito` conserva la unidad como `No disponible`. La comprobación y el cambio de estado forman parte de la misma transacción; ante un error, se revierten la venta y las unidades. Un cambio de comprador sin cambio de unidad no recalcula su estado.

Éxito: `200` con `{ ok: true, data: { codcor, tipo: "Individual", motivo, actor, reutilizada, operaciones } }`. Cada operación contiene relación anterior/nueva, versiones, estado de unidad origen antes/después, estado destino antes/después y la venta vigente resultante. El historial se registra como evento append-only.

## Preview y corrección coordinada

`GET /api/ventas/correccion-relacion/intercambio?codvenA=101&codvenB=102`

Devuelve `200` con el preview de ambas ventas. La confirmación exige exactamente dos operaciones y las dos unidades cruzadas:

`POST /api/ventas/correccion-relacion/intercambio`

```json
{
  "motivo": "Se cruzaron las unidades de dos compradores",
  "operaciones": [
    { "codven": 101, "versionEsperada": 2, "coduniNuevo": 42 },
    { "codven": 102, "versionEsperada": 5, "coduniNuevo": 41 }
  ]
}
```

Cada operación requiere `codven`, `versionEsperada` y `coduniNuevo`; `codcliNuevo` es opcional. La RPC verifica que cada unidad destino sea exactamente la unidad actual de la otra venta, que ambas ventas estén Registradas y que no exista un tercer compromiso. Las ventas se bloquean por ID y las unidades por ID ascendente. La unicidad de venta vigente por unidad se difiere dentro de la transacción para completar el intercambio atómico. Ambas unidades permanecen `Vendida`; no existe estado intermedio `Disponible`. Un evento `Intercambio` guarda los dos detalles bajo el mismo `codcor`.

## Historial

`GET /api/ventas/:codven/correcciones-relacion`

Devuelve `200` con una lista sanitizada de eventos: tipo, fecha, motivo, actor, relaciones anterior/nueva, versiones, estados y ventas que compartieron el evento. Las tablas son append-only, no tienen lectura/escritura directa para roles de aplicación, y se consultan mediante RPC.

## Dinero y cambio de comprador

Pagos, evidencia, adelanto de una separación convertida, importes pactados, snapshots y comprobantes permanecen asociados a la venta original. El adelanto no se copia ni se mueve; la separación convertida conserva comprador/unidad históricos y queda enlazada por `codsep` como antecedente. El historial HU-022 registra la relación de la venta antes y después.

Si cambia el comprador y hay pagos, adelanto confirmado o comprobante externo, la RPC solo acepta la corrección cuando el actor autenticado tiene rol **Gerente**. Una Administradora recibe `403` (`PT686`); no se crea un proceso de aprobación posterior. La confirmación del Gerente queda trazada en el evento.

## Errores principales

| HTTP | Códigos | Significado |
|---|---|---|
| `400` | `PT681` | Request/motivo incompleto o inválido; extras o UUID ausente también son `400` en Express |
| `403` | `42501`, `PT686` | Rol no autorizado o cambio financiero que requiere confirmación de Gerente |
| `404` | `PT680` | Venta inexistente |
| `409` | `PT438` | Techo físicamente instalado incompatible con el acuerdo de la venta |
| `409` | `PT683` | Relación cambió desde la consulta (preview obsoleto) |
| `409` | `PT684` | La corrección no cambia la relación actual |
| `409` | `PT685` | Unidad destino tiene compromiso vigente o no está disponible |
| `409` | `PT687` | Idempotency-Key ya fue usada con otra corrección |
| `409` | `PT688` | Unidad destino incompatible con el precio base pactado |
| `409` | `PT689` | La venta no está en estado Registrada |
| `409` | `PT690` | El intercambio no contiene exactamente las dos relaciones cruzadas |
| `409` | `PT692` | La separación antecedente no está Convertida |
| `409` | `PT693` | Configuración de techo de la unidad destino contradice el acuerdo de la venta |
| `409` | `23505`, `40001`, `40P01` | Conflicto de unicidad o concurrencia |
| `422` | `PT682`, `PT691` | Comprador inactivo/inexistente o unidad sin identificación válida |

Una Idempotency-Key con el mismo actor y payload devuelve el mismo evento con `reutilizada: true`. La misma key con payload distinto da `409`. Una key nueva vuelve a validar la versión actual; no repite una corrección anterior.

## Entrega / HU-032 pendiente

El checkout actual no tiene una fuente autoritativa de entrega real. La parte de CP-022-06 que requiere confirmar ausencia de entrega está **Bloqueada/No ejecutable**, no Fallida ni Aprobada. El backend **no infiere entrega** desde sede prevista, ubicación, movimientos, preparación, comprobante ni estado comercial. Un movimiento HU-003 activo sí impide devolver la unidad anterior a `Disponible`, pero no se interpreta como prueba de entrega. Cuando HU-032 se integre, la RPC de confirmación deberá volver a consultar la entrega efectiva (no basta el preview) y rechazar la corrección si cualquiera de las operaciones fue entregada, incluso si la entrega ocurrió después de abrir el formulario. No se debe simular esa fuente con otra columna o una inferencia.

## Pruebas de concurrencia

Los tests PGlite cubren transacción, locks declarados, stale version, replay, fallos con rollback y unicidad diferible. PGlite usa una conexión compartida, por lo que no sustituye una prueba futura con dos sesiones PostgreSQL independientes para doble confirmación y deadlock real.
