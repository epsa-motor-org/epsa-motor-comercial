# HU-032 / EMT-37 — Registrar la entrega de una moto vendida

## Alcance y fuente de verdad

`hu032_entrega` registra el hecho de entrega física. Una factura, pago, sede prevista, ubicación, movimiento o preparación no se interpreta como entrega. No se actualizan la venta, la unidad, pagos, adelanto, ubicación, movimiento, techo ni `preparacionunidad` al confirmar.

La modalidad acordada se lee de la anotación estructurada que ya guarda HU-006 en `venta.obsven`:

- `Entrega pactada (pendiente): se entregará armada en <sede>.`
- `Entrega pactada (pendiente): se entregará embalada en <sede>.`
- Se admite el prefijo histórico `Entrega acordada:` con el mismo texto posterior.

Si una venta antigua no conserva una de estas frases y tampoco hay otra fuente persistida, la modalidad queda sin determinar y la entrega se bloquea. No se deriva de contado/crédito ni de la preparación física.

La estructura no inventa una etapa física `Embalada`: HU-033 solo representa armado y techo. La fila de entrega registra la modalidad explícita `Embalada` y no cambia la preparación. No afirma que HU-033 haya confirmado embalaje, armado o instalación.

La tabla es append-only, tiene RLS habilitado, no concede acceso directo a `anon` ni `authenticated`, y solo se consulta o registra por RPC. Se conserva una entrega por venta. Una unidad puede acumular varias entregas históricas por ventas distintas si una entrega anterior fue cancelada y la unidad retornó; la FK compuesta mantiene la relación de cada entrega con venta, unidad y comprador. Las restricciones no permiten corregir o borrar una entrega existente.

## Estado y elegibilidad

`GET` distingue:

- `Vendida pendiente de entrega`: falta al menos una condición;
- `Lista para entrega`: acuerdo armado y condiciones físicas/comerciales completas;
- `Lista para entrega embalada`: acuerdo embalado, unidad recibida y sede válida;
- `Entregada`: existe una fila `hu032_entrega`;
- `Retornada`: hay una entrega histórica de una venta cancelada y HU-021 registró el retorno físico; `entrega` sigue presente, junto con `retorno`, ubicación actual y estado comercial actual;
- `Venta cancelada`: venta cancelada sin hecho de entrega.

Una entrega registrada se conserva aunque la venta se cancele. Antes de registrar retorno, la venta continúa proyectándose como `Entregada` con `estadoVenta: "Cancelada"`, y la unidad permanece bloqueada. Después del retorno la proyección superior cambia a `Retornada`; el objeto de entrega continúa indicando `Entregada` como hecho histórico, y el objeto `retorno` acredita el evento posterior. No se presenta como una moto todavía en poder del cliente.

Para ambas modalidades, la venta debe seguir `Registrada`, pertenecer al comprador y unidad enviados, y la unidad debe estar identificada y en estado comercial `Vendida`. `Por definir` bloquea ambas modalidades. La sede acordada debe ser una sede EPSA activa (`sede` activa y `ubicacion.tipubi = 'Sede'`); la ubicación actual de la unidad debe corresponder a esa sede. Ancón es `Almacen`, no una sede de retiro. Un movimiento HU-003 `Pendiente` o `En transito` bloquea la entrega. No se modifica ni cancela ese movimiento.

**Armada:** requiere `preparacionunidad.estarmado = 'Terminado'`. Para `Sin techo`, se permite la entrega cuando la preparación no registra un techo instalado: una configuración en `unidad.codtte` sin `preparacionunidad.esttecho = 'Instalado'` no prueba que esté instalado. Si la preparación confirma `Instalado`, GET devuelve `Vendida pendiente de entrega` y POST responde 409; HU-032 no desmonta ni cambia la unidad. `unidad.codtte` identifica el tipo configurado y `esttecho = 'Instalado'` es la evidencia física; un estado instalado bloquea `Sin techo` incluso ante una configuración inconsistente o nula. Tras el retiro físico, la preparación debe actualizarse mediante HU-033 (por ejemplo, retroceder a `Pendiente` con observación). Para `Con techo`, deben coincidir `unidad.codtte` y `venta.codtteven`, y `preparacionunidad.esttecho` debe ser `Instalado`. Un techo físico de otro tipo no satisface el acuerdo. GET y POST aplican la misma compatibilidad.

**Embalada:** requiere acuerdo explícito y recepción en la sede acordada, pero no requiere armado terminado ni instalación de techo. No escribe estados ficticios de preparación. El esquema actual no contiene una fuente física persistida que certifique que la moto está realmente `Embalada`: HU-032 conserva el acuerdo comercial `Embalada`, pero no afirma ni valida el embalaje físico.

La venta a crédito puede entregarse con saldo pendiente. La operación no cobra, convierte saldo en pago, recalcula importes ni altera pagos o adelanto.

## Contrato HTTP

Ambas rutas requieren `Authorization: Bearer <sesión Supabase>` y permiten Gerente, Administradora y Vendedor. La identidad/rol viene de HU-007 y PostgreSQL. El vendedor debe ser el `codusuresp` vigente al confirmar; ser autor anterior o haber abierto antes el formulario no basta. Gerente y Administradora no reasignan responsable mediante HU-032.

### Consultar

`GET /api/ventas/:codven/entrega`

Respuesta `200`:

```json
{
  "ok": true,
  "data": {
    "codven": "50",
    "coduni": "10",
    "codcli": "20",
    "estadoVenta": "Registrada",
    "estado": "Lista para entrega",
    "modalidadAcordada": "Armada",
    "sedeAcordada": { "codsed": "2", "nombre": "Ventanilla" },
    "ubicacionActual": { "codubi": "2", "sede": "Ventanilla" },
    "decisionTecho": "Sin techo",
    "preparacion": { "armado": "Terminado", "techo": "No requiere" },
    "entrega": null,
    "retorno": null,
    "estadoComercialUnidad": "Vendida",
    "condicionesFaltantes": []
  }
}
```

### Registrar

`POST /api/ventas/:codven/entrega`

Requiere `Idempotency-Key` como UUID único. Campos del body:

- requeridos: `coduni`, `codcli`, `modalidad` (`Armada` o `Embalada`), `fecha` (`YYYY-MM-DD`, fecha real no futura), `receptor`, `documentosPendientes` (boolean);
- opcionales: `observacion`, `observacionDocumentos`, `referenciaGuia`.

Ejemplo armado:

```json
{
  "coduni": 10,
  "codcli": 20,
  "modalidad": "Armada",
  "fecha": "2026-11-14",
  "receptor": "Comprador registrado",
  "documentosPendientes": false
}
```

Ejemplo embalado:

```json
{
  "coduni": 10,
  "codcli": 20,
  "modalidad": "Embalada",
  "fecha": "2026-11-14",
  "receptor": "Persona que recibe",
  "documentosPendientes": false,
  "observacion": "Entrega excepcional en embalaje original"
}
```

Ejemplo con documentos pendientes y referencia textual de guía:

```json
{
  "coduni": 10,
  "codcli": 20,
  "modalidad": "Armada",
  "fecha": "2026-11-14",
  "receptor": "Persona que recibe",
  "documentosPendientes": true,
  "observacionDocumentos": "Tarjeta y placa pendientes",
  "referenciaGuia": "GR-F001-000123"
}
```

Si se marcan documentos pendientes, se exige observación y una referencia textual de guía. La variante “guía por adjunto” solicitada por QA/PO **no está implementada**: el backend actual no tiene infraestructura de adjuntos reutilizable para una guía, y HU-032 no crea almacenamiento nuevo. No se carga un archivo. No se marcan tarjeta, placa, SOAT, notaría ni transferencia como completados.

Primera entrega: `201`. Reintento idéntico con misma clave: `200`, misma entrega. Misma clave con payload o actor distinto: `409 PT698`. Venta/unidad con una entrega distinta: `409` con `data.entregaExistente` cuando se puede proyectar.

## Errores HTTP

| HTTP | Código SQL | Significado |
|---|---|---|
| 400 | `PT694` | Fecha o datos inválidos |
| 401 | — | Falta o expiró la sesión; respuesta estándar HU-007 |
| 403 | `42501`, `PT697` | Rol/usuario no autorizado o Vendedor que dejó de ser responsable vigente |
| 404 | `PT695` | Venta inexistente |
| 409 | `PT696` | Venta, comprador, unidad, modalidad, ubicación, tránsito, techo o preparación no cumple condiciones actuales |
| 409 | `PT698` | Idempotency-Key reutilizada con otra solicitud |
| 409 | `PT700` | HU-022 intenta corregir/intercambiar una operación entregada |
| 409 | `23505`, `23503`, `40001`, `40P01` | Unicidad, relación o concurrencia; se devuelve mensaje seguro |

Errores desconocidos siguen siendo `500`; no se convierten arbitrariamente en conflictos.

## Integración con HU-021 y HU-022

HU-021 conserva `hu032_entrega` al cancelar una venta entregada y devuelve `entregaConservada`/`fechaEntrega`. La unidad permanece `Vendida` hasta el retorno físico. El endpoint existente `GET /api/ventas/:codven/entrega` conserva el evento de entrega y, después del retorno, añade el registro de retorno, la ubicación actual y la situación comercial; su estado superior pasa a `Retornada`.

El retorno se registra mediante `POST /api/ventas/:codven/retorno` (contrato y reglas en `docs/HU-021.md`), exclusivamente por Gerente. La RPC valida una venta cancelada con entrega HU-032, una sede EPSA activa, idempotencia y compromisos comerciales bajo locks. Solo actualiza la ubicación confirmada y el estado comercial de la unidad: no modifica la venta, cancelación, entrega, pagos, comprobantes, preparación, techo ni movimientos. Si no queda otra venta o separación activa, vuelve a `Disponible`; si existe otro compromiso, conserva `Vendida` o `Separada` según corresponda. La condición registrada describe el estado físico recibido y no crea por sí sola un bloqueo.

Tras el retorno, la unidad puede venderse y entregarse de nuevo. `202611190001_hu021_retorno_fisico.sql` elimina la unicidad global de entrega por unidad y ajusta la RPC HU-032 para conservar una entrega por venta. El ciclo mantiene ambos hechos: venta A/entrega A/cancelación/retorno y venta B/entrega B; no borra ni reemplaza la primera entrega.

HU-022 proyecta la entrega real desde `hu032_entrega`; el preview es informativo. Las RPC de corrección individual e intercambio verifican la entrega bajo los locks de venta/unidad antes de escribir. `PT700` bloquea ambos casos. Una FK compuesta aporta protección adicional si se intenta cambiar la relación por otra ruta SQL. La operación HU-032 usa el mismo orden de locks (unidad y luego venta); si compiten confirmación, cancelación o corrección, se serializan y la operación perdedora no deja cambios parciales.

## Pruebas y límites de verificación

La prueba de base de datos aplica el orden real de migrations hasta `202611150002`, luego `202611150003` y finalmente `202611190001` en PGlite. Cubre los escenarios vigentes de EMT-37, incluidos `Armada + Sin techo` compatible, el bloqueo cuando un techo anterior sigue instalado, la paridad de GET/POST y su elegibilidad posterior a la actualización física por HU-033; también cubre techo `Con techo` no instalado/exacto/distinto, embalada con/sin acuerdo, ubicación, identificación, preparación, permisos, idempotencia, conflictos, cancelación, retorno, reventa y conservación financiera/física. La variante de guía por adjunto y la verificación física específica de `Embalada` siguen limitadas por el modelo existente.

Los casos `Promise.allSettled()` de PGlite comparten una conexión/sesión y solo verifican el resultado de negocio más las restricciones locales. No demuestran concurrencia real de dos sesiones PostgreSQL/Supabase independientes. Las carreras de entrega y retorno deberán validarse en un entorno PostgreSQL real antes de afirmar que se probó concurrencia entre sesiones.
