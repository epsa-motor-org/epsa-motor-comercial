# HU-011 / EMT-16 — Consultas web con registro central

## Comportamiento

El visitante envía **Cotización** (modelo publicado obligatorio; comentario opcional)
o **Consulta general** (modelo opcional; mensaje obligatorio). Nombre, móvil peruano,
sede comercial activa y aceptación del aviso son obligatorios. Se aceptan 2–150
caracteres de nombre y hasta 500 puntos de código Unicode en el mensaje normalizado.
El teléfono admite `+51`/`51` y separadores habituales; se guarda como nueve dígitos.
No exige stock, correo, DNI, techo, pagos ni responsable al visitante.

La entrada es un `lead` Web/Nuevo/Sin asignar. No crea clientes, unidades, ventas,
reservas o seguimientos ficticios. El modelo puede ser NULL. La modalidad y el
mensaje quedan explícitos en `lead.obslea`; color, techo y forma de compra son
preferencias, nunca una venta o un precio vinculante. El texto de la consulta se
puede desplegar en el panel de interesados, renderizado como texto por React.

Gerencia/administración consultan mediante HU-015 y pueden asignar el mismo lead
conservando sede e identificador. Un vendedor solo consulta los que tiene asignados.
HU-035 podrá repartir posteriormente sobre ese registro; no bloquea HU-011.

## Contrato público Supabase RPC

`POST /rest/v1/rpc/web_registrar_interesado`, con clave pública del proyecto.
El navegador nunca recibe una clave `service_role`.

```json
{
  "p_nombre": "PRUEBA QA CODEX",
  "p_telefono": "+51 987 654 321",
  "p_codmod": null,
  "p_color": null,
  "p_codsed": 1,
  "p_detalle": "¿Cuál es el horario de atención?",
  "p_tipo": "Consulta general",
  "p_idempotencia": "386e16f3-1073-467f-b652-f5a69ec34c44",
  "p_acepta": true,
  "p_version_aviso": "2026-10",
  "p_contexto": null
}
```

Los once parámetros se envían explícitamente. Modelo/color/contexto admiten NULL.
`p_tipo` solo admite `Cotización` y `Consulta general`. `p_contexto` es texto
referencial opcional de hasta 300 caracteres, independiente del mensaje de 500.
Las sedes permitidas son Comas, Puente Piedra y Ventanilla activas; Ancón y fibreras
no son destinos de atención. Un modelo informado se comprueba publicado al guardar.

Respuesta: `{"codigo":"W-<UUID del envío>","repetido":false}`. No devuelve teléfono,
nombre, coincidencias de clientes, ID interno del lead ni datos del inventario.
La misma clave y payload canónico devuelve el mismo código y `repetido:true`.
Otra consulta legítima del mismo teléfono usa una clave nueva y NO sobrescribe
modelo, sede, mensaje o responsable de la anterior. Clave repetida con otros datos:
409. El replay se resuelve antes de comprobar referencias que pudieron desactivarse.

El formulario conserva la clave mientras el payload no cambia y no confirma éxito
si falta respuesta/acuse. No usa WhatsApp como sustituto silencioso de persistencia.
El enlace opcional a WhatsApp requiere una acción del visitante; no se envía nada
automáticamente. En demostración se identifica el guardado solo en el navegador.

| Estado / SQLSTATE | Significado |
| --- | --- |
| 200 | Guardado o replay válido |
| 400 / PT400 | Validación o aviso requerido |
| 409 / PT409 | Misma clave para otros datos |
| 429 / PT429 | Ventana de admisión completa; reintentar más tarde |
| 401 o 403 / 42501 | Acceso no autorizado; PostgREST devuelve 401 para anon y 403 con sesión autenticada |
| Red / 5xx | Sin confirmación; conservar formulario y clave para reintentar |

## Persistencia y seguridad

La migración incremental crea `hu011_envio_web`: clave UUID, lead asociado,
huella SHA-256 del payload normalizado, modalidad, versión del aviso y fecha del
servidor. La aceptación se registra con el envío; no acredita identidad del visitante.
La tabla tiene RLS y ninguna concesión directa a anon/authenticated. La función
definidora es deliberadamente pública solo para este registro acotado: fija origen,
estado y responsable; valida entradas y referencias; no acepta usuario, rol o estado
administrativo ni expone lectura de datos. Las firmas manuales mantienen permisos.

Un bloqueo transaccional por clave y la PK protegen la idempotencia. Lead y acuse
se guardan en la misma transacción. Se conserva el freno global legado de 40 nuevos
envíos en diez minutos, ahora serializado; un replay válido no consume otro cupo.
Este freno global no es protección completa frente a abuso distribuido; no se
incorpora CAPTCHA ni validación externa de identidad en esta historia.

La firma pública antigua de siete parámetros queda privada para cerrar la ruta
que fusionaba celulares por 24 horas y omitía aceptación/idempotencia. No ejecutar
de nuevo el bloque legado de `frontend/docs/supabase-sprint2-conexiones.sql` ni su
GRANT tras esta migración. Los scripts históricos no son la versión vigente.

## Aviso y entrega

Se mantiene el aviso existente y su versión `2026-10`, sin aceptación preseleccionada
ni texto legal nuevo. El PO debe revisar/conformar su contenido antes de publicar;
esta implementación no certifica cumplimiento legal ni reemplaza esa revisión.

Aplicar `20261116063202_hu011_consultas_web.sql` sobre el esquema vigente, revisar
ACL/RLS y publicar el frontend coordinadamente. No usar el frontend nuevo sin su
SQL. Formularios antiguos abiertos deben recargarse: la firma anterior deja de
aceptar escrituras públicas. La migración es reaplicable y no reclasifica ni fusiona
leads históricos. No se aplicó esta migración al proyecto compartido durante el
desarrollo. Revertir el frontend dejando el contrato antiguo revocado requeriría
restaurar una versión compatible; no reabrir esa firma por resolver un error de UI.


Las pruebas SQL usan PGlite con esquema, roles y perfiles sintéticos locales. Cubren
modalidades, límites, nombres, móvil, sedes, referencias, consentimiento, privacidad,
legacy RPC, replay/cambio de payload, rollback, asignación manual y regresión de alta
manual. La prueba de solicitudes paralelas usa una conexión PGlite; no acredita
concurrencia entre conexiones PostgreSQL independientes ni Supabase Auth/PostgREST.
Las pruebas frontend ejecutan los validadores compartidos y la demostración sin
ventas ni seguimientos. El recorrido de navegador debe registrar su transporte y
sesión: un adaptador local de RPC o sesión sintética no es un despliegue real.

Antes de aceptación final: migración y frontend integrados, pruebas bajo roles
reales autorizados, persistencia tras recarga, asignación desde HU-015 y retest de
dos solicitudes sobre el mismo envío con conexiones independientes. La DoD y los
14 escenarios de Jira conservan su alcance; este PR no declara aceptación del PO.
